# Spec: using the 1M-token context window

Status: v4. Three reviews by Opus 5.5 at high effort (19 + 12 + 10 findings, all addressed). T1, T4, T5 and T7 are built (889b749 and the commit after it); T2, T3, T6, T8-T13 are not. Builds on `Specs/eval-system/`, `Specs/harder-evals/` and `Specs/fresh-holdout-exam/`. Baseline: server 0.9.0 plus the accepted candidates.

## Research (2026-10-26)

Facts, with where they come from:

- The model in use is `deepseek-flash` = DeepSeek-V4.1-Flash-1017. Context length 1M tokens, maximum output 384K, thinking and non-thinking modes, tool calls supported. ([DeepSeek pricing page](https://api-docs.deepseek.com/quick_start/pricing))
- Price is flat in context length: no long-context tier. Per 1M tokens at peak: input cache hit $0.006, input cache miss $0.30, output $1.20 (off-peak is half). A cache hit is 50 times cheaper than a miss. (same page; `eval/pricing.json` agrees)
- The pricing page does not say how the cache is built or invalidated. Third-party listings (not DeepSeek) cite a 10 MB request cap and give max output as 384K or 393K. Treat both as unverified.
- No published long-context quality figure for this model was found. Whether more context helps this harness has to be measured.

What the server does today (`src/engine.ts`, `src/config.ts`, `src/context.ts`; checked in review):

| limit | value | effect with a 1M window |
|---|---|---|
| `compact()` starts | 220,000 characters of `JSON.stringify(messages)` (escaped, without tool schemas). Roughly 55-70K tokens is an estimate; measured in T10 | about 6% of the window |
| `compact()` cut | keeps the first two messages and the last six; scans from index 2; cuts a tool result to its first 3,000 characters plus a `[truncated N chars]` marker | see next row |
| `compact()` repeats | mutates the persistent message array in place on every turn. A cut message is still over 3,000 characters (3,000 plus marker), so the next pass cuts it again: the marker reads `[truncated 12345 chars]`, then `[truncated 24 chars]`, then `[truncated 21 chars]`, stable only from the fourth visit. Each pass subtracts the marker's 21 characters from its running size without removing anything, and `cut` counts raw characters while `size` counts escaped JSON | once over budget, nearly every turn changes history from the oldest uncut tool result (or a recent marker) onward, so the provider re-bills everything from the first changed message at the miss price. This is true and worse than first stated |
| `read_file` | 400 lines or 30,000 characters per call; a single longer line is sliced at the budget | a large file needs many calls |
| any tool result | 45,000 characters; a larger JSON result becomes an error plus a preview cut mid-string | |
| context pack | 6,000 characters (`CONTEXT_CHARS`; 0 disables) | small; untested whether more helps |
| output | `MAX_TOKENS` 32,000 with thinking on; `reasoning_content` is passed back and never compacted | far below the 384K maximum |
| time | `MAX_TURNS` 30, `REQUEST_TIMEOUT_MS` 300 s, job `TIMEOUT_MS` 900 s, runner `--task-timeout` 1200 s | a prompt near 1M tokens may exceed these |
| request body | tool output is JSON inside JSON (`packResult`, then `JSON.stringify(body)`), so escapes double | 800K tokens is about 3.2M raw characters, a body of roughly 4-7 MB |
| other caps | `DIFF_CHUNK`, `DIFF_CAP` 600, `run_tests` tail 60 lines, gate test tail 40 lines | |

The server reads `prompt_tokens`, `prompt_cache_hit_tokens` and reasoning tokens from each reply and puts them in the trace; compaction ignores them.

## Goal

Let the harness use a large window sensibly: keep what the model has read instead of cutting it at 6% of the window, keep the provider's cache intact, and show with the eval whether that improves correctness or lowers cost. If it does not, say so and keep the current defaults.

## Non-goals

- No change of model, roles, gates, prompts or the allowed-paths rules.
- No automatic stuffing of the whole repo into the prompt.
- No model-written summaries of old context (a possible later step).
- No change to the keep-rule thresholds, and no use of `confirm.ts` on setting arms (see AC-8).

## Acceptance criteria

- AC-1. Defaults unchanged. Every limit in the table above is a setting whose default is today's behaviour. `CONTEXT_MODE` (`legacy` default, or `extended`) selects the cutting style: `legacy` keeps today's marker churn, in-place mutation and mid-line slices exactly; `extended` is the new behaviour of AC-3 and AC-4. With no setting changed, compaction and tool results are identical to before. Test oracle: a frozen copy of the old `compact()` in the test file, run the way the engine runs it (called every turn on the same growing message array, its return value ignored, the array mutated in place), compared with the new code over growing multi-turn synthetic conversations (there are no recorded ones; traces keep summaries only). Each setting has its own type and range: integers >= 1 under a hard ceiling for sizes, with 0 accepted where 0 already has a meaning (`CONTEXT_CHARS`, `MAX_REPAIRS`) or means off (`CONTEXT_TOKENS`, `JOB_INPUT_TOKEN_CAP`, `MAX_REQUEST_BYTES`), and a fraction in (0,1] for `COMPACT_LOW` (unset = off). `src/config.ts` gets `loadContextSettings(env, maxTokens)` so refusals can be tested. A bad value does not throw at import (the eval runner, the tests and `smoke.ts` import `CFG` too): `configProblem` holds the message, defaults are used, and the server's start-up refuses to run. `CONTEXT_TOKENS` needs `CONTEXT_MODE=extended`; `CONTEXT_TOKENS` and `CONTEXT_WINDOW` are both set or both unset; `COMPACT_LOW` unset means off.
- AC-2. Token-aware compaction (a new mode, on only when `CONTEXT_TOKENS` is set). `CONTEXT_TOKENS` and `CONTEXT_WINDOW` must be set together; one without the other is refused at start-up. The budget must leave room for `MAX_TOKENS` plus a margin of 50,000 tokens inside the window. The mode works from the last reported `prompt_tokens` plus an estimate for messages added since (using the measured characters-per-token ratio from T10), and falls back to characters when usage is missing.
- AC-3. Cache-friendly compaction (new modes only). Only in `CONTEXT_MODE=extended`: a message that was cut is marked (in a side set, not in the message sent to the API) and never changed again; the marker is fixed text; sizes are tracked in escaped JSON length consistently. With `COMPACT_LOW` set, compaction cuts oldest-first down to `budget * COMPACT_LOW` so it runs rarely. Test on a synthetic 40-turn conversation that grows past the budget: with the watermark set, the number of turns on which the earlier prefix changed is at most half of the number without it, and no cut message is ever modified again. If, after cutting every cuttable tool result, the estimate is still over the budget, the job ends as exhausted with the reason `context_budget`. Assistant messages and `reasoning_content` are never cut: DeepSeek's thinking-mode guide says `reasoning_content` must be passed back in full in later requests of a tool loop, and a request without it is answered with HTTP 400. (A placeholder for old reasoning is not tried unless the T10 probe shows the API accepts it.)
- AC-4. Read and result caps (`read_file` characters and lines, tool result limit) are settings; the numbers apply in both modes. At the default numbers in `legacy` mode behaviour is unchanged. In `extended` mode, paging works at every value and a result is cut only at a line boundary, except that a single line longer than the cap is cut with a visible marker.
- AC-5. Job input-token guard. `JOB_INPUT_TOKEN_CAP` (default off). Before each request, if the cumulative reported input tokens (the last `prompt_tokens` added to the running sum) are already at or over the cap, the job ends like the turn limit does (`exhaustedReason` `input_tokens`; a request-size refusal ends it as `request_size`, and a spent token budget as `context_budget`, so none of them is dropped as an infrastructure error): it reaches the gates as an exhausted job (so the one-writer and commit rules are unchanged), with a clear reason and the cumulative input tokens in the report (the server has no price table, so cost is computed by the eval). The overshoot is at most one request.
- AC-6. Observability. A trace event records each compaction (turn, messages cut, characters or tokens removed). `score.ts` reports per run and per task: peak prompt tokens, cache-hit share of input, number of compactions, repeat reads (a read whose path and the line range actually returned overlap an earlier read of the same path, not ordinary paging; the trace summary of `read_file` therefore records the returned from/to), reasoning tokens, `truncated` events, and timeouts. They appear in the report and compare tables. Traces from before this change still score.
- AC-7. Evidence tasks. At least six extra-large dev tasks (hard tier, axis `long-context-xl`). The committed fixture is a small seed; the task's `setup.ts` expands it deterministically to 300,000-800,000 characters of original filler and commits the result in the temp repo (so the gates see a clean tree). Scenarios: a needle in a very large file; a cross-file change in a repo larger than the old compaction limit; a long job whose early reads matter after the old limit would have cut them; and three more varying these. Each has hidden checks, a reference, two decoys of different kinds. `task.json` records the expected size and a sha256 of the expanded output (generated paths and bytes, before any overlay) and `--validate` checks it. Because validation expands each task once per variant (6 tasks x 4 variants = 24 expansions), the expansion is fast and the full `--validate` time is measured against its budget. The sha256 is over the sorted list of `<posix path>\0<bytes>\0` for every generated file. The needle tasks are not solvable by one lexical `grep` (the tool skips lines of 2,000 characters or more and files over 1 MB, and the needle must need reasoning, not a keyword). Files edited by the reference or decoys stay small. The generator is part of the task-set hash. AC-13 of `Specs/harder-evals/` is amended to cover "seed plus generator", not the expanded repo (an edit to that spec made in T9), and these tasks are exempt from the harder-evals AC-10 structural retune (a retune must not shrink them); their calibration spend is budgeted in T11. They are also excluded from the hard-tier counts of AC-11 (8 of 12 calibrated), AC-12 ($2 and 90 minutes per k=5 run) and AC-14 (`--validate` under 3 minutes), by amendments made in T9; they have their own budget approved by the owner, and `calibrate.ts` needs 10+ baseline runs of them before the freeze (T17).
- AC-8. Dose-response experiment, with the screening decision made on one pre-registered comparison. Arms, all on the same server code and differing only in recorded settings: (a) baseline = defaults; (b) caps-only = raised read and result caps, `CONTEXT_MODE=extended` and the old character budget (so the only difference from (c) is the budget and the watermark); (c) primary = token budget 250K with the watermark and matching caps; (d) top = the smaller of the budget the measured request ceiling allows (AC-10) and the peak prompt tokens the pilot actually reached, no higher than 800K; dropped if it is under 1.5 times (c), because a flat curve would only waste the spend. Run on the six XL tasks at k=10, plus a regression slice (and any harder-evals long-context or larger-repo task that exists when the plan is written) at k=5. The task list is fixed in `experiment.md` before any spend, together with the job count, the expected wall-clock time and the concurrency (about 300 XL jobs and 200 slice jobs plus pilot and calibration, run one at a time, is tens of hours and in the range of $150-500; the pilot replaces this guess). Only (c) vs (a), counted over the XL tasks alone, can screen the setting in; the other tasks are a guard: a second compare run on all non-XL tasks (`--exclude-axis long-context-xl`) must show zero counted losses at the normal delta (floor tasks excluded from losses as usual), and no gain on them counts. The false-block rate of the guard is stated in `experiment.md`. A negative control comes first, over all tasks: the baseline is run twice (a1, a2) and a2 against a1 must not screen as KEEP; the (c) comparison pools both baseline runs (`--baseline a1,a2`). (b) and (d) are reported, as attribution (is it the caps or the budget?) and as the dose-response curve, and carry no decision. `compare.ts` gets a task filter (by axis or task list) for this. Timeouts (`TIMEOUT_MS`, `REQUEST_TIMEOUT_MS`, the runner's task timeout, and the proxy's upstream timeout, now a setting instead of the fixed 330 s) are raised identically in every arm including the baseline and are all recorded in the manifest, and `JOB_INPUT_TOKEN_CAP` is set identically in every arm. The comparison uses `compare.ts --dev-only`, and its verdict is printed as a SCREENING verdict: with no held-out guard it is never a KEEP in the sense of the loop. The real KEEP is the normal comparison, with held-out guard, of the candidate branch that changes the defaults. A setting arm is never run through `confirm.ts`: confirmation would re-run both sides with the process environment (`confirm.ts:135`), ignoring the settings. Adopting a setting means changing defaults in a normal candidate branch, which has a new code hash and goes through the usual loop and confirmation. All of this spec's arms share one code lineage and so draw on that lineage's single held-out budget; settings do not buy new looks.
- AC-9. Cost rule. A setting is adopted only if its hidden-pass result passes the keep rule AND (its mean cost per run is at most 1.5 times the baseline's, or the owner accepts the rise after seeing it). Cost uses the measured cache-hit and miss split and `eval/pricing.json`. The estimate before any spend is written into the experiment plan. Worst case for one 30-turn job at 800K tokens: 24M input tokens cost $7.20 if all are cache misses or $0.14 if all hit, plus up to $1.15 output (30 x 32K tokens), about $8.35; a timed-out request is retried up to 4 times and billed each time, and multi-step tasks multiply it. A run whose context ramps up (average about half the maximum) at 90% cache hits is near $0.75 per job; the pilot replaces both guesses with a measurement. the run uses `--max-cost`, and a pilot at k=1 comes first. A cap that stops an arm half-way excludes that arm instead of scoring it. Runs excluded as infrastructure (timeouts, the job deadline) are counted per arm, and a verdict is refused when the exclusion rates of two compared arms differ by more than 10 percentage points, because a large-context arm that times out would otherwise look better by losing its worst runs. The $2 per run limit of `Specs/harder-evals/` AC-12 does not apply to this experiment; it has its own budget approved by the owner.
- AC-10. Transport limits. The real request-size limit is probed against the API (needs the owner's approval to spend) before arm (d) is chosen; the top arm is derived from the measured ceiling. `chat()` checks the serialized body size before sending and refuses with a clear error above `MAX_REQUEST_BYTES` (default 0 = off, so defaults are unchanged; the experiment sets it from the measured ceiling). The probe goes through the proxy with `--max-cost`, never with a raw key, and uses content with many bytes per token so that the byte ceiling is not confused with the 1M-token window. The longest turn latency at each arm is recorded.
- AC-11. Settings reach the arms correctly. The new settings are added to the runner's allowlist so manifests record them (together with `--task-timeout`, which is not recorded today); a per-task `env` override of any of them is refused by the loader (it is not recorded in the manifest and would hide a difference between arms).
- AC-12. `npm test` stays green, new code has unit tests, `--validate` stays offline and within its time budget, and no safety rule is weakened (caps, denied paths, one writer, commit rules, key handling).

## Constraints

- TypeScript run by Node type stripping, erasable syntax only, no new runtime dependencies.
- The API key stays in the proxy; any spend needs the owner's approval of an estimate.

## Interaction with `Specs/harder-evals/`

- The XL tasks should be authored before `harder-evals` T17 (calibration freeze), or that freeze is redone. They count in the task-set hash, along with their generator.
- Calibrated at defaults they will probably be `floor` tasks. A floor task that rises still counts as a gain (right for this experiment); a floor task that falls is not counted as a loss, so these tasks cannot flag a regression by themselves. The regression slice carries that role.
