# Plan: using the 1M-token context window

Implements `Specs/long-context/spec.md` (v4, after three reviews).

## Approach

First make the limits settings with unchanged defaults and keep the old compaction as an exact "legacy" mode, selected by `CONTEXT_MODE` (default `legacy`; `extended` turns on the new cutting style). Add new modes (token-aware, cache-friendly) beside it, plus a job guard, a pre-send size check and metrics. Then build large fixtures. Then find the real request ceiling, run a cheap pilot, and run the experiment with the existing loop. Only if the one pre-registered comparison passes the keep rule and the cost rule do the defaults change, and that change is a normal candidate branch (new code hash, usual loop and confirmation). Setting arms never use `confirm.ts`; their comparison is a screening verdict (`--dev-only`, no held-out guard), and the real KEEP is the candidate branch's normal comparison.

1. **Settings.** (built) `src/config.ts` gains `loadContextSettings(env, maxTokens)` and `configProblem`; a bad value is refused at server start-up, not at import; and `CONTEXT_MODE`, `COMPACT_CHARS`, `COMPACT_LOW` (watermark fraction, 0 = off), `CONTEXT_TOKENS` (0 = off) with `CONTEXT_WINDOW` (required together), `READ_BUDGET_CHARS`, `READ_MAX_LINES`, `RESULT_LIMIT_CHARS`, `MAX_REQUEST_BYTES`, `JOB_INPUT_TOKEN_CAP` (0 = off). `CONTEXT_CHARS` and `MAX_REPAIRS` keep 0 as valid; each setting has its own type and range (sizes >= 1, 0 meaning off where stated, `COMPACT_LOW` a fraction in (0,1], unset = off). `CONTEXT_TOKENS` needs `CONTEXT_MODE=extended`. `MAX_REQUEST_BYTES` defaults to 0 (off). Defaults are today's constants.
2. **Compaction.** `src/compact.ts` holds a compactor created per job (`createCompactor(settings)`): it owns the state the new modes need (the side set of cut messages and the index of the last reported usage), and is called each turn with the message array. It is not pure in legacy mode: `engine.ts:466` calls `compact(messages)` every turn, ignores the return value and relies on the in-place mutation of the persistent array, so legacy mode keeps exactly that (the oracle test runs it the same way over growing multi-turn conversations). Legacy reproduces `engine.ts:413-425` including re-cutting and the `[truncated N chars]` churn. Extended mode: fixed marker, cut messages tracked in a side `WeakSet` (never added to the message sent to the API) so they are never touched again, size in escaped JSON length, when every cuttable tool result is already cut and the estimate is still over budget the job ends as exhausted with the reason `context_budget` (`reasoning_content` is never dropped: the API answers 400 without it in a tool loop); token budget from the last `prompt_tokens` plus an estimate for what was added since, watermark cut-down. Returns the messages plus a record of what it cut (for the trace).
3. **Caps.** `READ_BUDGET`, the line window in `read_file`, `RESULT_LIMIT` come from config and apply in both modes. Legacy mode keeps the mid-line slice and the mid-string preview; extended mode cuts at line boundaries (a single over-long line is cut with a marker). The trace summary of `read_file` records the returned from/to.
4. **Job guard and size check.** (built) `runAgent` checks before each request whether the running input sum is at or over `JOB_INPUT_TOKEN_CAP`; if so the job ends as exhausted (same path as the turn limit; the exhausted text at `gates.ts:283` is hard-wired to MAX_TURNS and `AgentOutput.exhausted` in `src/types.ts` is a boolean, so both gain a reason), with the reason and cumulative input tokens reported (cost is computed by the eval, which owns the price table). `chat()` measures the serialized body and refuses above `MAX_REQUEST_BYTES` when it is set; `runAgent` turns that refusal into an exhausted ending with reason `request_size`, so the run is scored as a failure instead of being dropped as infrastructure.
5. **Metrics.** Trace event `compact` (add to `TraceEvent` in `src/types.ts`). `score.ts` adds peak prompt tokens, cache-hit share, compactions, overlap-based repeat reads (using the returned from/to), reasoning tokens, `truncated` events and timeouts, with the old-trace case reading as absent; compare tables get the columns.
6. **Runner and compare support.** New settings added to the runner allowlist (`eval/lib/proc.ts`), recorded in manifests together with the runner task timeout; the proxy's upstream timeout (fixed 330 s at `eval/lib/proxy.ts:82`) becomes a setting; the task loader refuses the new settings in `task.env`. `compare.ts` gets `--dev-only` (the `devOnly` code path exists at `compare.ts:50,181`; the CLI skips `spendLook`, passes `devOnly`, and labels the verdict SCREENING) and a task filter by axis or list. The pre-registered decision counts the XL tasks only; other tasks act as a loss guard.
7. **Fixtures.** (`runSetup` runs after `makeRepo` has committed the seed at `fixture.ts:83-84`; the generator must commit in `setup.ts`.) Six XL tasks. Each task's `setup.ts` expands a small seed deterministically (seeded generator, original text, near-duplicate names, plausible code) and commits it in the temp repo. `task.json` stores the expected size and sha256 of the expansion; `--validate` checks them. The generator lives where `taskSetHash` covers it (the task-set hash is extended to include the generator files; today it walks only the hard task folders). The sha256 in `task.json` covers the generated paths and bytes before any overlay. The needle edits made by references and decoys sit in small files.
8. **Measure the transport.** A characters-per-token measurement on the generated filler against the API (also needed for the token estimate), a real request-size probe, and the longest-latency check. These spend a little and need approval.
9. **Pilot, then experiment.** Pilot k=1 across the four arms to catch broken scenarios and to calibrate the cost estimate (the estimate includes up to 4 retries of a timed-out request). A negative control: baseline run twice, the second against the first must not screen as KEEP. Then the full experiment: baseline, caps-only, primary (250K, watermark, matching caps), top (derived from the measured ceiling). XL tasks at k=10; a regression slice (and any harder-evals long-context or larger-repo task that exists) at k=5, with the list fixed in `experiment.md` before spend. All timeouts (including the proxy's) and `JOB_INPUT_TOKEN_CAP` identical in all arms. Screening decision: (c) vs (a) over the XL tasks only, keep rule plus cost rule; the other tasks are a loss guard. (b) and (d) are reported for attribution and dose-response.
10. **Adopt or not.** If adopted, the owner decides defaults (Q1, Q2) and a normal candidate branch changes them; the owner merges.

## Data and API changes

- Environment settings only; no MCP tool or schema change.
- Trace gains one event type; score rows gain numeric fields; manifests already record settings.
- Job reports gain an "input token cap reached" reason; `chat()` gains a request-size refusal.
- `task.json` of XL tasks gains `expanded: { bytes, sha256 }`.

## Test strategy

- `compact.test.ts`: a frozen copy of the old `compact()` as the oracle; legacy mode equals it on synthetic conversations (various sizes, tool result lengths, short lists); token mode with and without usage; fixed marker and no re-cut in new modes; watermark gives at most half as many prefix-changing turns on a 40-turn synthetic conversation; never touches the system message, the first user message or the last six; a malformed list does not throw.
- `config.test.ts`: defaults equal today's constants; 0 accepted where it has a meaning and refused elsewhere; `CONTEXT_TOKENS` without `CONTEXT_WINDOW` refused; a budget with no room for `MAX_TOKENS` refused.
- `read_file`: paging at default, 5x, 20x; line-boundary cuts in non-default mode only (AC-4). Job guard: a mock model asking for large reads ends with the cap reason, reaches the gates as exhausted, commit rules unchanged; with the cap off, unchanged (AC-5). Size check: `chat()` refuses an over-limit body.
- Score tests: peak tokens, cache share, overlap-based repeat reads, old traces (AC-6).
- Runner tests: settings recorded in manifest; per-task `env` for these settings refused (AC-11).
- Fixture tests: generator is byte-stable; expansion size and sha256 match `task.json`; `--validate` passes for all six; the committed folders are small (AC-7).
- Full `npm test`, smoke and `--validate --split all` before any spend.

## Risks

- **Quality may fall with more context** (distraction, slower turns). Mitigation: dose-response arms, a pre-registered single decision, the keep rule.
- **Power and false keeps.** With three tasks a KEEP is not reachable; with six XL tasks at k=10 a large true effect is detected with high probability (estimated by the reviewer at about 78-100% for effects of 0.3-0.6) and the false-KEEP rate on mid-band tasks is a few percent. Noisy k=5 tasks would raise it (about 10% with four mid-band tasks), so they only act as a loss guard and never count toward a gain. A negative control (baseline against baseline) checks this. A later `--final` statistic is a separate step after adoption.
- **Multiple comparisons.** Three arms against one baseline would triple false keeps. Mitigation: only the primary arm decides.
- **Cost.** About $8.35 worst case per 30-turn job at 800K tokens before retries (a timed-out request can be sent and billed up to 4 times), about $0.75 if the context ramps and 90% of input hits the cache; multi-step tasks multiply it. Mitigation: estimate before spend, `--max-cost`, identical `JOB_INPUT_TOKEN_CAP`, pilot first, a capped arm is excluded, not scored.
- **Confounding.** Budget and caps move together. Mitigation: the caps-only arm. Timeouts raised identically everywhere; reasoning tokens, truncated events and timeouts reported per arm.
- **Cache behaviour is undocumented.** The saving is inferred from the two prices and the shape of the conversation. Mitigation: report the measured cache-hit share per arm; claim only what is measured.
- **Request size, `reasoning_content` and timeouts at the top arm.** Assistant messages and `reasoning_content` are never cut (and must not be: the API rejects a tool loop without them), so a budget can be unreachable; the job then ends as `context_budget`. Timeouts and the job deadline become infrastructure exclusions; they are counted per arm and a verdict is refused when two arms differ by more than 10 points. Mitigation: real probe first (AC-10), top arm derived from it, pre-send check, latency recorded.
- **Fixture realism and drift.** Generated filler may be too easy; a shared generator can change silently. Mitigation: near-duplicate names, two decoys, size and hash in `task.json`, generator inside the task-set hash.
- **Overlap with `Specs/harder-evals/`.** Mitigation: separate axis `long-context-xl`, authored before the calibration freeze or the freeze is redone; floor-task behaviour noted in the spec.
- **Settings and the held-out budget.** Arms share one lineage. Mitigation: exploration uses `--dev-only`; only the candidate branch that changes defaults spends looks.
- **Staleness.** Valid for this model only. Mitigation: settings, not hard-coded values; the model is recorded in the report.

## Task breakdown rationale

Settings and the legacy-exact compaction come first because everything depends on them and they can be proven identical to today's behaviour offline. New modes, guard and size check follow. Metrics and runner support come before fixtures so the first fixture run shows what happened. Transport measurements precede the experiment because they set the top arm. The pilot precedes the full run because it fixes the cost estimate. Anything that spends waits for the owner.
